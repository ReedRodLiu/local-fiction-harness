# 项目方案：本地优先 AI 文游

## 项目方向

初期重点服务女性向 AI 文游玩家，尤其是已有剧本、角色设定和长对话存档、希望继续延续故事的用户。DeepSeek 网页端限额带来的迁移需求是当前切入机会；产品长期价值仍需通过真实玩家验证。

产品按市场反馈分三阶段演进：

1. **文游播放器**：导入已有自然语言剧本指令与历史存档，继续演绎故事，支持独立故事管理、流式回复、本地自动存档、撤回重写与分支回溯、基础剧情摘要记忆以及模型 API 配置。
2. **文游 Harness**：强化长上下文窗口工程、长期记忆召回、角色一致性（防 OOC）、文风控制、剧情分支树与世界状态管理。
3. **文游游戏引擎**：探索自然语言规则解析、确定性数值结算、事件触发系统、创作者工具与剧本生态。只有前两阶段得到正向反馈后再立项。

## 用户体验与运营边界

- **本地优先、无业务服务器**：剧本、剧情、存档和记忆保存在用户设备本地；API Key 仅保存在用户端。项目方不自建业务服务器、不托管用户剧本与对话数据、不做大模型中转商、不代付或转售模型额度，也不售卖第三方剧本内容。
- **BYOK（自带 API Key）**：用户直接配置自己拥有的模型服务商 API Key 并由客户端发起请求。本路线不绕过 DeepSeek 网页端限额，也不承诺免费模型调用；普通玩家对配置 API Key 与直接承担调用费用的接受度需要尽早验证。
- **轻量、开箱即用与最小权限**：面向希望省事开箱即用的普通文游玩家，不要求玩家先安装电脑客户端或远程连接电脑，也不打包 Ubuntu/PRoot、Node.js 运行时，不开放任意 Shell 或动态代码执行能力。
- **不考虑微信小程序**：结合技术与合规调研（[最小客户端技术讨论依据](research/2026-11-17-client-runtime-options.md)、[微信小程序合规调研](research/2026-11-17-miniapp-compliance.md)），小程序存在 `request` 合法域名白名单（难以支持用户任意自定义中转 API 地址）、200 MB 本地用户文件上限、非个人主体才能申请“深度合成”类目及需提供技术主体合作协议与算法备案等门槛，与“纯本地、无中转后端、灵活 BYOK、低成本轻启动”冲突，因此明确排除微信小程序路线。
- **法律与合规保持边界意识**：即使采用纯本地运行、用户自带 API Key 与用户自行导入剧本，减少开发方托管与分发行为，也不自动等同于免除生成式 AI 服务标识、拟人化互动合规（含 2026 年 7 月 15 日施行的《人工智能拟人化互动服务管理暂行办法》）或著作权相关注意义务。在面向公众正式发布前，仍需针对实际发布形态完成合规与版权核查。

## 技术路线：自研轻量文游 Harness

### 为什么放弃 DSH 底座

此前方案曾评估将开源 DeepSeek Harness（DSH）及第三方 Android 移植版（DSH Mobile）作为运行底座。经源码与运行时调研确认：

- DSH 本质上是面向编程与通用桌面智能体的运行时（依赖 Cordis 插件容器、Node.js、本地子进程与工具执行），即便是 `@deepseek-ai/dsh-sdk-minimal`（`0.2.2-rc.1`）仍包含本地子进程、Shell/终端与 `danger-full-access` 文件系统配置。
- `DSH Mobile` 完整发布包需捆绑 Bionic Node.js 运行时（官方发布说明标注完整 APK 约 156 MB、存储需求约 720 MB，且 `targetSdk 28` 侧载策略不直接满足应用商店合规），在 iOS 上更会受到禁止子进程与动态执行代码的沙盒限制。
- DeepSeek 等模型的 `/chat/completions` 本身是无状态 HTTP API，完全可以由客户端自行组织和回传多轮上下文。

对普通女性向文游玩家而言，真正有价值且需要定制的并不是通用 Agent 的插件生态或 Shell 执行，而是针对长篇互动叙事的上下文组装、防失忆摘要、分支回溯和状态维护。因此，项目决定**彻底放弃 DSH 底座，转向自研轻量文游 Harness 与纯本地存储**。

### 核心架构与分步载体策略

核心思路是**将“纯逻辑层文游 Harness”与“端侧壳/UI”彻底解耦**：

1. **核心文游 Harness（纯 JS/TS 逻辑模块）**：
   - 剧本与存档解析：支持直接粘贴及纯前端解析 `.docx` / `.md` / `.txt` 自由格式剧本；导入时由 LLM 拆解生成结构化故事蓝图供确认与展示，同时在对话上下文中完整保留原始剧本全文作为兜底锚定。
   - 上下文编排（Context Engineering）：采用「固定锚定区（原始剧本与轻量约束）+ 滚动剧情摘要区 + 近期对话窗口」三区结构，控制 Token 预算并防止长篇细节遗忘。
   - 故事分支与状态树：支持本地自动保存、撤回重写、多平行时间线分支；回溯时同步回滚对应范围的剧情摘要，防止时间线污染。
   - 无状态模型接口层：通过标准 HTTP/SSE 流式对接 DeepSeek 及主流 OpenAI 兼容接口（含 `content` 与 `reasoning_content` 兼容解析），不依赖 Node.js 后端特有 API。
2. **第一步（当前优先）：本地网页端最小实现**：
   - 采用 `Vite + React + TypeScript`（`src/harness/` 与 `src/ui/` 解耦）先在本地网页跑通核心源码与第 1 阶段文游播放器闭环，数据落盘浏览器 IndexedDB，API Key 默认存 `localStorage` 并提供“仅当前会话内存有效”开关与风险提示。
   - 同步验证本地开发代理与纯浏览器直连模型接口时的 CORS 跨域行为（如已实测测试端点千帆 `deepseek-v4.1-flash` 无浏览器 CORS 头，开发期需通过 Vite 本地代理转发）。
3. **第二步（按需推进）：最小化 Android 封包**：
   - 当网页端闭环跑通、需要打包发给种子用户在手机上真机试用时，将已跑通的网页核心放入极薄的 Android 原生容器（如 Capacitor 等轻量方案）。
   - 借助原生 HTTP 网络层绕开浏览器 CORS 限制（支持用户直连 DeepSeek 官方或自定义的兼容 API 地址），并逐步接入原生持久化与系统安全存储保管 API Key。
4. **暂缓范围**：iOS 原生适配与商店上架、复杂数值规则引擎、创作者平台与剧本交易市场均不在本轮最小实现范围内，待本地网页闭环和种子用户验证有正向结果后再单独评估立项。

## 首批验证与后续门槛

Wayfinder 开发地图以新路线重新设置首批验证：

1. **本地网页端最小文游 Harness 跑通**：完成核心源码实现与浏览器内故事闭环，验证自由剧本拆解、原文兜底锚定、摘要回溯和本地存储。
2. **DeepSeek 官方 API 专项联调**（依赖网页核心跑通）：对比评估 DeepSeek 官方接口与测试替代模型在剧本拆解、文风遵循与 CORS 上的差异。
3. **Android 最小封包验证**（依赖网页核心跑通）：验证极薄原生壳在实体设备上的直连网络（无 CORS 阻塞）、本地恢复、安全存储与包体表现。
4. **用户 BYOK 与发行合规调研**（可并行）：验证普通女性玩家配置 API Key 的门槛、真实设备分布与留存痛点，并明确公开发行前的合规与版权检查清单。

上述核心闭环和用户验证获得结论后，再决定正式 MVP 的设备范围、收费与发布策略。
