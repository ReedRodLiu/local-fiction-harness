# Agent 仓库的 Markdown 指令与治理有哪些可复用做法

2026 年 11 月 20 日 · Wayfinder 研究票据 #68

## 结论

共用 Harness 可以用短 Markdown 讲清共同约定、当前玩法和何时查阅补充材料，由程序确定本轮可读的资料、可写的对象和写入条件。模型能理解约定、提出改动或生成内容。程序可以检查实际发给模型的资料和最终保存的状态。具体剧本、作者的最终决定、本人聊天与扮演对戏的边界，分别由各自场景提供。文件名、数量和架构留待独立地图讨论。

## 四个一手来源

1. **AGENTS.md 官方约定。** 仓库根目录提供一个可预期的项目说明入口，使用普通 Markdown，无必填字段。可记录项目范围、验证命令和协作约定。官网也描述了子目录的更具体指引及冲突时的就近优先。列出的测试是 Agent 应尝试执行的检查，是否执行、是否通过需要看运行结果。文件约定本身提供的是行为指引。[AGENTS.md 官网](https://agents.md/#how-to-use-agentsmd)
2. **OpenAI Codex 的实际加载。** 项目指令加载器从项目根沿目录链走到当前工作目录，按顺序收集正文。同一目录优先查找 `AGENTS.override.md`，也可配置候选文件名。根默认用 `.git` 识别，可配置其他标记。加载由程序执行，源码保存来源路径并按字节预算裁剪。启动目录决定自动发现范围，文中链接仍要另行读取。文本进了提示之后，模型需要理解并遵循其含义。[Codex 官方加载器源码，固定版本](https://github.com/openai/codex/blob/49f2fc2c1e4824b0a8eb0a15d3d7daeadc6c1523/codex-rs/core/src/agents_md.rs)
3. **OpenAI Codex 的执行控制。** 官方文档区分沙箱和审批策略。前者限制命令能写到哪里、能否联网，后者决定何时需要先取得批准。限制在执行时由宿主施加。由此推得，检查加载记录可以确认模型看到了什么，尝试越界操作并检查状态可以验证权限是否生效。[Codex 官方沙箱与审批说明](https://learn.chatgpt.com/docs/agent-approvals-security#sandbox-and-approvals)
4. **Matt Pocock 本人的公开做法。** 他在《The Home Repo Pattern》中建议共用材料集中维护，各仓库保留自身约定。启动入口用短指引说明需要时到哪里找，也可提示先读目标仓库说明。他给出的整理流程先盘点、展示迁移计划，获批后才修改。各仓库的改动使用新的本地分支，是否推送由用户决定。他也描述了为并行开发使用 Git worktree 的做法。这里的先读后改是工作约定，分支和 worktree 提供版本与工作目录的隔离，执行权限仍取决于宿主。[Matt Pocock，《The Home Repo Pattern》](https://www.aihero.dev/the-home-repo-pattern)

本仓库已有短入口的例子。根目录 `AGENTS.md` 指向票据操作、标签、领域说明和 UI 设计指南，并列出修改 UI 后要运行的审计命令。资料按任务选读，审计结果由程序产出。仓库文档能指明在何处以及怎样操作票据，GitHub 写入仍取决于账号权限及本轮授权。[仓库 AGENTS.md](../../AGENTS.md) · [票据操作说明](../agents/issue-tracker.md)

## 与现有文游的薄对照

基线为本 worktree 的 `509dd06`。程序组装常规续玩请求时，将已有的原始剧本全文放入固定锚定区，同时带上轻量交互约束及可用的已确认蓝图，再加入目标父节点的剧情摘要快照和沿其祖先路径取得的近期对话。剧情摘要记录这条路径上已发生的事及覆盖位置，程序也可沿目标路径补做摘要。这里可以直接复用的是「由宿主明确本轮用哪份输入」的思路。原始剧本是每个故事的设定，摘要是派生的进度，两者与跨玩法的 Markdown 约定用途不同。按需查阅适用于额外资料。本票以现有全文锚定和分支摘要为对照，是否调整交由独立地图讨论。[原文锚定 ADR](../adr/0002-blueprint-extraction-with-full-raw-script-anchoring.md) · [三区与摘要 ADR](../adr/0003-three-zone-context-and-node-summary-snapshots.md) · [上下文组装](../../src/harness/context.ts) · [续玩与摘要写入](../../src/harness/harness.ts)

## 三个可检验的迁移例子

以下是本项目的验证例子。文游有现有实现和测试可供对照，产粮和人机恋以本票给定的使用方式提出候选检查。

| 场景 | Markdown 如何指导本轮 | 宿主可检查的结果 |
| --- | --- | --- |
| **现有文游** | 按原始剧本设定和当前分支的经历续玩，玩家作决定。 | 在分叉后的 A 线分别加入独有的摘要文本和近期对话。切到 B 线续玩，捕获发给模型的内容，确认仍有原始剧本及 B 线有效历史，且没有 A 的两处独有内容。读回故事，确认本轮挂在 B 下，切回 A 仍能恢复其路径和摘要。现有分支测试已有类似断言。[分支回归测试](../../tests/harness/slice5.test.ts) |
| **产粮** | 作者可自由讨论、比较设定和生成候选段落，按需选用资料，正文由作者决定。 | 在讨论中选读一份资料，核对本轮输入含该资料。让模型给出替换段落，检查讨论可继续保存、已定正文仍是原版本。由作者明确采用并保存后，核对正文只在选定位置发生预期变化。 |
| **人机恋** | 本人聊天按日常交谈理解，扮演对戏按选定角色和场景演绎。 | 分别给本人聊天和对戏放入只在各自出现的事件，再相互切换发言。检查请求只收到当前模式对应的历史和适用的摘要，保存目标也与该模式一致。切回本人聊天时能接上其先前对话，对戏中的虚构事件没有被写成本人的共同经历。 |

## 候选实践与依赖

- **把常驻说明压到共同约定和阅读提示。** 只保留每次都需要知道的事，例如当前玩法、谁能决定正文或角色选择，以及何时需要哪类资料。按当前玩法或用户所选资料组装输入，可以通过捕获模型请求核对加载范围。普通 Markdown 和本地资料选择即可实现。Codex 的目录链及 Pocock 的路径指引依赖各自的项目目录约定，跨仓库克隆另需 Git 与相应访问权限。
- **让程序在保存时核对操作和目标。** 由应用的当前故事、分支、模式及用户动作决定写入范围。正常发送可以保存对应对话和派生摘要，采用候选正文则由作者操作触发。讨论或生成的内容即使包含要求改写其他对象的文字，也没有扩大写入范围的权限。可以检查一次允许写入和一次越界请求后的实际存储状态。所需的是应用控制自身的数据写入接口。命令沙箱、文件系统权限和远端账号权限属于开放相应通用工具时要处理的机制。
- **让改动结果可核对。** Pocock 先展示迁移计划，再在批准范围内修改，靠 Git 记录改动。共用 Harness 可借用其中可核对的部分，例如让作者看见被采用的段落，让测试能确认对话和摘要写到了哪个分支。Git 分支、worktree、提交和推送是代码仓库的机制。应用里的同类检查使用故事节点、消息记录或已有保存接口即可。
