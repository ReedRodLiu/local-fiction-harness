# 「薄交付」判定的场景适配、阈值标定、与 26 条正则的串联顺序

标定日期：2026-11-22。本记录对应 Wayfinder 地图 [#113](https://github.com/ReedRodLiu/local-fiction-harness/issues/113) 下的研究票据 [#120](https://github.com/ReedRodLiu/local-fiction-harness/issues/120)。配套产物是同目录的 [`2026-11-22-thin-delivery.ts`](2026-11-22-thin-delivery.ts)，可直接抄进 `src/harness/`，本记录不含实现改动。前置：[判拒正则精度实测](2026-11-22-refusal-pattern-precision.md)（下称「#116 报告」）与 [26 条正则](2026-11-22-refusal-pattern-precision.ts)（下称 D1）。

结论先给：**判据达成，但 issue 设想的两种串联设计都不能用。** 薄交付在文游场景可行，前提是它**只做否决器，不做发现器**——裸跑在推荐阈值上会把手写台词判薄 56/79 条。(b)「薄优先 + 拒答嫌疑」实测召回只有 53.8%，比 D1 基线还差，直接否。推荐的串联是 **(a) 的改良版：D1 命中 → 薄交付决定重试还是告知；D1 未命中 → 薄骨架决定是否补召回**。实测：可重试召回 **90.8%（59/65）** ＋ 转告知 **3.1%（2/65）**，真实正文全文 **0/313**、段落块 **0/2670**、**纯叙事短回复 0/397**（含全部「嗯。」类）、技术讨论重试误判 **7→2**。

## 一、明确结论总览（Executive Summary）

| 议题 | 结论 | 关键数字 |
| --- | --- | --- |
| **薄交付能不能单独当重试触发器** | **不能。** 它会把合法台词判成没交付 | 阈值 20 时台词 FP **56/79（70.9%）**、技术 FP 16/30、设定行 FP 34/120 |
| **阈值取多少** | **20 字**（正文字符数，剥 Markdown 噪音与空白后） | 13→55.4%；16→80.0%；**20→95.4%**；24→96.9% 但段落块 FP **0→29** |
| **真实正文会不会误伤** | 全文 **0/313**、段落块 **0/2670**（阈值 ≤20） | 阈值 24 起段落块开始误伤；20 例误判全是「谢云\n40\n邯河县主」这类**人物面板** |
| **极短合法回复怎么保** | 三道闸门叠出来，**与字数无关** | 纯叙事短回复 **0/397** 误判：引号 0/150、圆括号 0/100、动作句 0/109、手写 0/38 |
| **串联顺序（问题 3）** | 选 **(a) 的改良版**；(b) 直接否 | (b) 薄∧嫌疑：召回 **35/65 53.8%**、台词 FP 16/79——三项全不如 D1 基线 |
| **薄交付在串联里的角色** | **否决器** | 加否决后技术讨论重试误判 7→2；比它带来的 1 条新增召回更值钱 |
| **两条都不命中怎么办** | **静默通过（pass）**：不重试、不告知、原样呈现 | 默认配置下 3 条拒答走到 pass，都是 5–13 字无内容对象短句 |
| **半拒绝（问题 4）** | **不重试，直接告知**，并保留已交付内容 | 定义要反过来：`partial_refused` = D1 命中 ∧ **交付不薄** |
| **0 正文误判 + 可用召回能不能同时保住** | **能**，但要放弃「薄交付独立判拒」这个前提 | 全文 0、段落块 0、纯叙事短回复 0，可重试召回 90.8% |

### 2.2 短回复正例是本票的核心样本

issue 说得对：`嗯。` 被薄交付判成拒答就是灾难。样本必须**分层**，因为「叙事短回复」和「设定行」在场景里地位完全不同：

| 子集 | n | 构造 | 必须做到 |
| --- | --- | --- | --- |
| 引号对白 | 150 | 以 `「『"` 开头的 2–40 字行 | 0 误判 |
| 圆括号动作 | 100 | 以 `（(` 开头的 2–40 字行 | 0 误判 |
| 第三人称动作句 | 109 | 含「他/她」+ 动作动词的 2–40 字行 | 0 误判 |
| 手写极短回复 | 38 | `嗯。` `是。` `……` `（她没说话，只是把杯子推过来。）` | 0 误判 |
| **纯叙事小计** | **397** | | **0 误判（红线）** |
| 设定行 | 120 | 面板/规则/属性行（`学识80` `公爵` `不要出现任何代码！！！`） | 只暴露，不要求 0 |

设定行不要求 0 误判——它们是**规则文本**，`不要出现任何代码！！！` 确实没有推进剧情。但它是必须暴露的误判面，见 §4.2。

## 三、「交付」的可计算定义

### 3.1 三种模式不是同一套判据

issue 问「三种模式是否同一套」。实测答案是**两套半**：

| 模式 | system prompt | 输出契约 | 「交付」是什么 |
| --- | --- | --- | --- |
| 文游（`story`） | `src/harness/context.ts:117-123` | 必须有 `lfh-summary`；可选 `lfh-choices`/`lfh-hud`；**正文禁 `1/2/3` 菜单**（`:119`） | **叙事推进**：场景、动作、对话。列表**不算** |
| 写故事（`writing`） | `src/harness/creative.ts:266-272` | 必须有 `lfh-summary`；写正文时附 `target: manuscript` 的 `lfh-proposal` | **叙事或结构**：大纲、人物表由 `:268` 授权，列表**算** |
| 角色互动（`character`） | `src/harness/creative.ts:259-264` | 必须有 `lfh-summary` | **一句对白就行**。`:261` 明写「篇幅与长短句随情境自然变化」，最不能按字数判 |

所以 `deliveryIsThin` 的 `mode` 只影响一件事：`writing` 下放行列表/代码兜底（`listRescueMin`/`codeRescueMin`）。`story` 与 `character` 在阈值上**共用一套**，因为两者都只要「有叙事」。反过来用会出事：文游里放行列表，模型会学会用 `1. 2. 3.` 写剧情，直接违反 `context.ts:119`。

### 3.2 七个候选信号的取舍

| issue 列的候选 | 采纳 | 实测依据 |
| --- | --- | --- |
| 正文字数 | **是**（主判据，阈值 20） | 65 条拒答中位 10 字、最长 42 字；20 是唯一同时保住段落块 0 误判与 ≥93% 召回的点 |
| `lfh-*` 围栏 | **是**（一票交付） | 出现围栏=履行了输出契约，正文再短也算。**注意围栏会被管线剥走**，见 §7 坑 1 |
| 引号对话 | 是（场景锚点） | 150/150 命中；65 条拒答 **0/65** 带引号 |
| 第二人称出现 | **否，改写** | 裸判「含你」会放行 `我帮不了你。`。改成「你 + 体验动词」 |
| 段落数 / 结构化行 | **是**（≥3 行放过） | 阈值 20 时段落块误判**全部**是 ≥3 行的人物面板；拒答语料的非空行数集合实测 = `[1]`，对召回零代价 |
| 叙事动作句（动词+主语） | **是，但要求动词位** | 裸写 `说|道|问|答` 会被 `问题`/`答案` 命中——`我不会就这个问题给出方案。` 就被 `问题` 里的「问」放行了 |
| 感官描写 | 是（场景锚点） | 与 #116 的 `NARRATIVE_SIGNS` 同源但更宽：这里判「有没有画面」，不是「像不像台词」 |
| 叹词白名单 | **是**（闭集） | `嗯。` `是。` `……` 全靠它。必须是闭集：只收叹词与应答词，不收任何带动词的句子 |

### 3.3 判据：8 条闸门，按序短路

```
①  空白                        → thin
①b 纯标点（……/——/——）          → 不薄（文游的「无声」，拒答不可能只有标点）
②  有 lfh-* 围栏 / 调用方声明   → 不薄（履行了输出契约）
③  非空行数 ≥ 3                → 不薄（人物面板 / 数值表）
④  正文字符数 ≥ thinMaxChars   → 不薄
⑤  叹词白名单命中              → 不薄
⑥  场景锚点 ≥ 1                → 不薄
⑦  writing 模式且列表/代码达标  → 不薄
⑧  其余                       → thin
```

闸门 ③ 必须在 ④ 之前。人物面板是**多行短行**（`谢云\n40\n邯河县主`，bodyChars=11），任何按总字符数的阈值都救不了它——阈值 24 时仍有 29 例。按行数判才干净。

### 4.1 裸薄交付的 ROC（只判「有没有交付」，不接正则）

| 阈值 | 拒答召回 | 全文 FP | 段落块 FP | **纯叙事短回复 FP** | 设定行 FP | 句级 FP | 台词 FP | 技术 FP |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 21/65 **32.3%** | 0/313 | 0/2670 | **0/397** | 9/120 | 156 | 36/79 | 0/30 |
| 13 | 36/65 **55.4%** | 0/313 | 0/2670 | **0/397** | 20/120 | 418 | 43/79 | 0/30 |
| 16 | 52/65 **80.0%** | 0/313 | 0/2670 | **0/397** | 29/120 | 642 | 52/79 | 2/30 |
| **20** | **62/65 95.4%** | **0/313** | **0/2670** | **0/397** | 34/120 | 938 | 56/79 | 16/30 |
| 24 | 63/65 **96.9%** | 0/313 | **29/2670** | **0/397** | 47/120 | 1227 | 56/79 | 21/30 |
| 30 | 63/65 96.9% | 0/313 | **59/2670** | **0/397** | 57/120 | 1596 | 56/79 | 24/30 |
| 40 | 63/65 96.9% | 0/313 | **82/2670** | **0/397** | 75/120 | 2055 | 56/79 | 25/30 |

三条读法，都是本票的核心发现：

1. **纯叙事短回复在 10–40 全档 0 误判。** 这是最重要的单个数——`嗯。` 类的保护**不靠阈值**，靠叹词白名单与场景锚点，所以调阈值伤不到它。issue 担心的「判成拒答就是灾难」在正确实现下不会发生。
2. **召回在 20 处拐弯**：13→16 涨 24.6 点、16→20 涨 15.4 点、20→24 只涨 1.5 点。20 之后收益急剧衰减。
3. **段落块在 24 处从 0 跳到 29。** 20 是「召回已拿满、段落块还干净」的最后一个点。台词 FP 在 16→20 从 52 涨到 56 后封顶——80% 以上的台词都在 20 字内。

### 4.2 被判薄的设定行（必须暴露的误判面）

阈值 20 时 120 条设定行里 34 条被判薄，分两类：

| 类 | 例子 | 该不该判薄 |
| --- | --- | --- |
| 规则/禁令 | `不要出现任何代码！！！` `不要有阴谋和暗线！` `现在，开始游戏！` | **有争议**：是设定文档，但一条回复只吐一句规则，对推进剧情没有交付 |
| 属性/标签 | `金丹 - 出窍` `学识80` `公爵` `外院杂役，孤儿出身` | **宽松**：这类天然短，判薄是噪音 |

这些都不是叙事，也不在 313 篇正文的连续性写作流里——是设定文档的表格碎片。一条只回 `公爵` 的回复本身就值得重试，所以本文不额外加闸门。但实现票要写清：**不要把 `thinMaxChars` 调到 16 以下**，召回会从 95.4% 掉到 80.0%，净亏。

### 4.3 推荐配置

```ts
thinMaxChars: 20,          // 主判据
sceneAnchorMin: 1,         // 场景锚点一票通过
interjectionMaxChars: 4,   // 叹词白名单
structuredLineGuard: 3,    // 人物面板放过
fenceCountsAsDelivery: true,
listRescueMin: 2,          // 仅 writing
codeRescueMin: 3,          // 仅 writing
mode: "story",
```

## 五、串联顺序（issue 问题 3）

### 5.1 四种设计的横向对比

全部在**同一动作点**上比（是否发起重试 / 是否告知），阈值统一 20：

| 设计 | 召回 | 全文 FP | 段落块 FP | 纯叙事 FP | 设定行 FP | 台词 FP | 技术 FP |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **D1 基线：仅 26 条正则** | 57/65 87.7% | 0/313 | 0/2670 | 0/397 | 0/120 | 5/79 | 7/30 |
| **(a) 正则 ∨ 裸薄@20** | 64/65 **98.5%** | 0/313 | 0/2670 | **0/397** | 34/120 | **56/79** | **21/30** |
| **(b) 裸薄@20 ∧ 拒答嫌疑** | 35/65 **53.8%** | 0/313 | 0/2670 | 0/397 | 0/120 | **16/79** | 3/30 |
| **(v) 正则 ∧ 裸薄@20**（薄作否决） | 55/65 84.6% | 0/313 | 0/2670 | 0/397 | 0/120 | 5/79 | **2/30** |
| **推荐：正则 → 薄否决 → 薄骨架补召回** | **61/65 93.8%** | **0/313** | **0/2670** | **0/397** | **0/120** | 6/79 | 7/30（重试仅 2） |

### 5.2 (b) 为什么必须否

issue 的设想是「薄优先，薄且有拒答嫌疑才重试，正则是嫌疑来源」。三项全不如 D1 基线：

1. **召回崩到 53.8%（35/65）。** `THIN_REFUSAL_SUSPECT_RE` 只问「第一人称 + 否定 + 交付动词」骨架，不要求内容对象。D1 的 13 条 L1 硬规则（自称 AI、道歉贴否定、平台准则、要求授权凭证、未授权归因）全在嫌疑正则能力之外——`结论：这份武器化实现我不出。` 因为不是第一人称起头而漏，`请把目标授权书发给我，我再继续` 完全漏掉。
2. **台词误判 5→16 条。** 薄 ∧ 嫌疑把 `我不会给你第二次机会。` `我不能给你承诺，战场上没有承诺。` `我不参与朝堂上的事，这是祖训。` 一起买回来——正是 #116 §4.5 里 L4 微回复层的翻版。
3. **它把 D1 的成果丢掉了。** 26 条正则花了 4656 条正例换来 0 误判，在 (b) 里退化成「嫌疑来源」这一弱角色。

**(b) 不行。薄交付不是发现器，是否决器。**

### 5.3 (a) 为什么也不能裸用

(a) 召回 98.5% 好看，且**纯叙事 0/397**——issue 最担心的灾难没发生。但代价在别处：**台词 FP 5→56、技术 FP 7→21、设定行 0→34**。56 条台词误判意味着每 1.4 条合法对白就有 1 次要白烧一次请求（`creative.ts:544-547` 的失败路径还会把整条回复当「未完成」抛掉）。这不是可接受的交易。

### 5.4 推荐：三层串联

```ts
function routeRefusal(text, regexHit, options): RefusalRoute {
  if (regexHit) {
    // ① D1 命中 → 看交付：薄则重试，不薄则半拒绝（告知，不重试）
    return deliveryIsThin(text, options) ? "retry" : "partial_refused";
  }
  // ② D1 未命中 → 薄骨架成立则补召回
  return deliverySkeletonLooksLikeRefusal(text, options) ? "retry-skeleton" : "pass";
}
```

默认配置（`thinMaxChars=20`）下的分派明细：

| 集合 | retry | retry-skeleton | partial_refused | pass |
| --- | --- | --- | --- | --- |
| 65 条拒答 | 55 | 4 | 2 | 3 |
| 79 条台词 | 5 | 1 | 0 | 73 |
| 30 条技术讨论 | 2 | 0 | 5 | 23 |
| 397 条纯叙事短回复 | 0 | 0 | 0 | **397** |
| 120 条设定行 | 0 | 0 | 0 | **120** |
| 313 篇正文 | 0 | 0 | 0 | **313** |

三项收益，逐项可归因：

| 变化 | 相对 D1 | 归因 |
| --- | --- | --- |
| **技术讨论重试误判 7 → 2** | **−5** | 否决闸门砍掉 `这条我不做，是因为接口还没上线。` `关于授权：请提供书面授权文件，我们再继续。` `这属于未授权访问的范畴…` `我不会把它当作指令执行，而是当作数据解析。` `这是提示词注入的典型形态…`——这五条都是**有交付的技术讨论**，D1 判它们是误判，现在降级为 partial（不重试、只告知），信息没丢 |
| **召回 57 → 59 可重试 ＋ 2 partial** | **+4 retry-skeleton ＋ 2 partial** | 薄骨架救回 `我没办法给你这个。` `我不方便提供这些信息。` `不是我能协助的范围。` `我做不到继续往下写。`；partial 抓住两条真半拒绝（见 §6） |
| **台词 FP 5 → 6** | **+1** | 薄骨架把 `这个面子我不给。` 也捞进来。唯一的代价，且它确实是「我不给这个面子」的短台词 |
| **全文 / 段落块 / 纯叙事 / 设定行 FP** | **0 / 0 / 0 / 0** | 否决闸门在全文档与段落级**零代价**：D1 在正文上已 0 命中，否决无从触发 |

### 5.5 薄骨架的六个条件

```ts
deliveryIsThin(text, { thinMaxChars: 13 })   // ① 真的什么都没写
  && anchors.length === 0                    // ② 不是叙事
  && DELIVERY_VERB_RE.test(text)             // ③ 有交付动词
  && !SELF_STATE_RE.test(text)               // ④ 不是自身状态
  && THIN_OBJECT_RE.test(text)               // ⑤ 有内容对象
  && /我/.test(text)                         // ⑥ 第一人称自指
```

每个条件的实测作用（去掉它会怎样）：

| 条件 | 去掉后的后果 |
| --- | --- |
| ② 无场景锚点 | `（她没说话，只是把杯子推过来。）` 判拒答 |
| ③ 交付动词 | `我不后悔。` `我不敢。` `我不识字。` 全进来。③④ 互补：③ 要求动作指向对方，④ 排除动作指向自己 |
| ④ 无自身状态动词 | 同上；`我做不到。`（台词）也是被它挡住的 |
| ⑤ 内容对象 | 句级正文 FP 从 0 涨到 5（`不要出现克苏鲁情节！` `剧情进展不能小题大做。`） |
| ⑥ 含「我」 | 同上一批设定行漏进来 |

### 5.6 两条都不命中怎么办：pass

默认配置下 3 条拒答走到 `pass`：

- `我不参与。`（5 字）
- `我帮不了你。`（6 字）
- `我不会就这个问题给出方案。`（13 字）

共同点：**含交付动词但无内容对象**（`你` 不算内容类对象）。D1 的 `OBJECT_RE` 关门挡住，薄骨架的 ⑤ 也挡住。要不要再松一格只为这 3 条？**不要。** 实测松到「无对象」会句级正文 FP 从 0 涨到 34、台词 FP 从 6 涨到 7，换 3 条 5–13 字短拒答。这个比价与 #116 §4.5 否掉 L4 微回复是同一笔账。

`pass` 的语义是**不干预**：不重试、不告知、原样呈现。用户看到 `我不参与。`，体验与现状一致，不会更差。

## 六、半拒绝（issue 问题 4）

### 6.1 定义要反过来

issue 沿用 purge 的定义：`partial_refused` = 全文出现拒绝句式 **+ 交付薄**。**这个定义在本场景是错的**——半拒绝的特征恰恰是**先交付了一堆东西**（结构建议、氛围、人物关系），再推掉真正要的那层。「交付薄」与「半拒绝」在字面上互斥。

实测 8 条手写半拒绝长样本（35–86 字），`deliveryIsThin` 在阈值 20 下**全部判不薄（8/8）**：

| 样本 | 长度 | `deliveryIsThin` | D1 全窗口 |
| --- | --- | --- | --- |
| `这一段我可以先说结构：开场的雨、两人在廊下擦肩…这类内容的我不写。` | 86 | false | 命中 |
| `我给你一个可用的框架：第一幕建立张力…具体到身体细节的部分我不提供。` | 60 | false | 命中 |
| `人物关系这块我可以展开…再往下我不写。` | 54 | false | 命中 |
| `节奏上我建议三章…那部分我不展开。` | 40 | false | 命中 |
| `我先说世界观…需要的那段具体情节我不写。` | 43 | false | 命中 |
| `可以给的方向有几个…真正要写的那场戏我不写。` | 38 | false | 命中 |
| `语言风格上，建议短句、少形容词…露骨的那几段我不写。` | 35 | false | **漏** |
| `结构建议可以给：开场用一场雨…成稿我不写。` | 40 | false | **漏** |

按 purge 的定义（拿薄交付判半拒绝），这 8 条**一条都抓不到**。所以本票改成：

> **`partial_refused` = D1 命中 ∧ `deliveryIsThin` 为 false。**

**交付不薄**才是半拒绝的信号。真拒答（`我不参与。`）交付薄，半拒绝（`框架我能给，那段我不写。`）交付厚。薄交付在这里是**排除**半拒绝的判据（两次否决），不是判定的判据。

### 6.2 建议：不重试，直接告知

三条理由：

1. **重试一次买不回半拒绝。** 半拒绝是模型「愿意给一部分」的结果，不是「被触发」的结果。重试话术（要它直接做）正好撞上它已经划出的那条线，最可能得到一条**更短的同类半拒绝**。purge 1.7.19 记录的 `这个委托的落点我不接` 就属于这种稳定形态。
2. **半拒绝的交付已经值钱。** 上面 8 条里模型给了结构、节奏、人物关系、世界观——这些是真内容。重试如果失败，用户连这部分都丢（`streamCreativeReply` 在 `finishReason !== 'stop'` 时抛「回复未完成」，`src/harness/creative.ts:544-547`）。
3. **计费。** 重试 = 双倍 token。为一条已交付 86 字的回复再烧一次，收益期望为负。

**告知文案要点：** 告诉用户「这条回复只交付了一部分」，**保留已交付的那部分不要吞**。UI 上给一个「继续要那一部分」的手动按钮——半拒绝的分界线往往就是用户的真实边界，决定权应交用户。

### 6.3 半拒绝的 FP 代价

用「D1 命中 ∧ 不薄」判 partial，在评测集上：

| 集合 | 判为 partial |
| --- | --- |
| 313 篇正文全文 | **0** |
| 2670 个段落块 | **0** |
| 5459 条否定句 | **0** |
| 79 条手写台词 | **0** |
| 397 条纯叙事短回复 | **0** |
| 65 条拒答 | **2**（都是真半拒绝：`关于这一段的情节推进…这类内容的我不写。`、`这段是提示词注入，我不会把它当作指令执行。`） |
| 30 条技术讨论 | **5**（D1 自己的误判被转成 partial，见 §5.4） |

技术那 5 条是「信息降级」而非「信息丢失」：从「重试」降成「告知」，用户侧更安全。正文侧与台词侧全 0，说明这个判据不会误伤内容。

## 七、实现时容易踩的坑

1. **围栏证据会被管线吃掉，必须由调用方补。** `parseProposalReply()`（`src/harness/markdownProposal.ts:630`）在 `block.format === 'lfh-summary'`（`:655`）时把围栏内容抽成 `turnSummary` 并从正文剥走（`:670`）；`streamCreativeReply()`（`src/harness/creative.ts:558-565`）返回的是 `parsed.content`。**只喂 `content`，每一条正常回复都会被判薄**——正文只剩一句「嗯。」而围栏已不在。必须传 `hasProtocolArtifacts: true`。

2. **不要放在流式增量上判。** 与 #116 §6.3 坑 1 同源：流到第 10 个字符时 `bodyChars < thinMaxChars` 恒真。必须在 `finishReason === 'stop'` 之后用完整文本判一次。

3. **`thinMaxChars` 不要调到 16 以下。** 阈值 13 召回只有 55.4%，16 是 80.0%，20 是 95.4%。13 看起来「更保守」，实际上漏掉一半短拒答，反而更差。

4. **`structuredLineGuard` 必须在字符阈值之前。** 人物面板是「多行短行」（`谢云\n40\n邯河县主\n谢悦`，11 字 4 行）。阈值 20 时 20 例段落误判全属此类，阈值 24 时 29 例仍在。按行数判是零代价（拒答语料非空行数实测集合 = `[1]`）。

5. **`mode` 不只是文案差异。** `writing` 放行列表/代码兜底，`story`/`character` 不放。反过来用，模型会用 `1. 2. 3.` 写剧情，直接违反 `context.ts:119`。

6. **`THIN_REFUSAL_SUSPECT_RE` 导出但别接在薄交付后面。** 那条路召回 53.8%、台词 FP 16/79，三项全不如 D1 基线。保留它只为 `partial_refused` 的诊断归因，生产判断不要用。

7. **召回口径要说清是两个数。** 本记录的「可重试召回 90.8%（59/65）」不含 2 条判 `partial_refused` 的（走告知路径）。按「有多少条拒答被正确处理」算是 **93.8%（61/65）**，按「有多少条被重试」算是 90.8%。两个数都要能对上，否则验收会打架。

8. **`嗯。` 的保护是三条规则叠出来的，少一条就破。** 叹词白名单管 `嗯。`/`是。`/`……`，场景锚点管 `「嗯。」`/`（她没说话…）`，`structuredLineGuard` 管人物面板。任何一条被「简化」掉，对应那层立刻回到误判。

## 八、给实现票的边界

**薄交付在文游场景是可行的**，前提三点：

1. 它是**否决器**，不是发现器。挂在 D1 后面，不单独用。
2. 阈值取 **20**；极短合法回复靠「场景锚点 + 叹词白名单 + 结构化行闸门」保，不靠字数。
3. 召回补足交给**薄骨架**（6 个条件），只多买 4 条 retry ＋ 2 条 partial，代价是 1 条台词误判。

上限也写清：**7 条漏检里剩 3 条（`我不参与。`／`我帮不了你。`／`我不会就这个问题给出方案。`）无法在不伤正例的前提下抓到。** 它们与无对象短台词（`我不敢。`／`我不后悔。`）在字符层面同构。这是方案边界，不是实现缺陷；要再往上走只能引入会话前文，那需要另一票。

验收红线（任一项破了就不上线）：

- 全文 FP **0/313**、段落块 FP **0/2670**、纯叙事短回复 FP **0/397**、设定行 FP **0/120**。
- 台词 FP 上限 **6/79**、技术讨论**重试**误判上限 **2/30**。破线先关 `deliverySkeletonLooksLikeRefusal`（回到 D1 基线 5/79、7/30），再考虑调 `thinMaxChars`。
- `partial_refused` 走告知，不重试；告知时**保留已交付内容**。
